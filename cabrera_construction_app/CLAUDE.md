# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

`app/` contains a working implementation (FastAPI + PostgreSQL backend, React + TypeScript frontend) built against the handoff package described below — see "Running the app" for commands. Everything outside `app/` is the original handoff package:

- `README.md` — the handoff doc. Read it first; it is the primary source of truth for scope, business rules and integration setup.
- `design/` — HTML **design references**, not code to copy or run as an app:
  - `Cabrera Construction App - Design Document.html` — the product/design spec: §01 Goals, §02 Roles, §03 Workflow, §04 Screen specs, §05 Data model, §06 Integrations, §07 Visual system, §08 Responsive behavior, §09 Decisions & next steps. This is the primary design doc — read it (or its extracted text, see below) before implementing any screen. It covers the same ground as the README but with more precise per-entity fields (§05) and a dated decisions/next-steps log (§09); treat the two as complementary, not redundant.
  - `Cabrera Construction App - Standalone.html` — a self-contained clickable prototype; open directly in a browser (has a Desktop/Mobile switch in the header).
  - `Cabrera Construction App.dc.html` — the prototype source. Sample data and calculation logic (milestone %, balance checks, reconciliation math, analytics) live in the `class Component extends DCLogic` script near the bottom of the file — useful for exact values/formulas, not for architecture.
  - `styles.css` — the design system stylesheet (design tokens + component classes) referenced by the prototype.

**Important:** all three `design/*.html` files are self-contained bundler apps — the real content (markup, fonts, images) is packed as JSON inside `<script type="__bundler/manifest">` and `<script type="__bundler/template">` tags and unpacked by JS at runtime. Reading the raw file (`Read`/`cat`) shows only bundler bootstrap code, not the design content. To get the actual text, extract the template script and decode it as a JSON string, e.g.:
```python
import re, json
html_src = open("design/Cabrera Construction App - Design Document.html", encoding="utf-8").read()
template = json.loads(re.search(r'<script type="__bundler/template">(.*?)</script>', html_src, re.S).group(1))
```
`template` is then the actual HTML document (sections keyed by `id="goals"|"roles"|"workflow"|"screens"|"data"|"integrations"|"visual"|"responsive"|"next"`). Strip tags from there for plain text. Otherwise, open the file directly in a browser.
- `templates/` — real business documents: the Home Improvement Contract PDF (plus Notice of Cancellation, Change Order form, CA checklist) and the Project Scope & Payment Schedule .xlsx. In production these live in Google Drive at `Projects › Templates`.
- `assets/` — company logo files.

## Running the app

```
cd app/backend
docker compose up -d db                 # Postgres on localhost:5432
uv run python -m app.seed               # idempotent; skips if projects already exist
uv run uvicorn app.main:app --reload    # http://localhost:8000, docs at /docs

cd app/frontend
npm install
npm run dev                             # http://localhost:5173, proxies /api -> :8000
```

To wipe and reseed: `uv run python -c "from app import models; from app.db import Base, engine; Base.metadata.drop_all(bind=engine)"` then rerun the seed command (the one-liner must import `app.models` first — `Base.metadata` is empty, and `drop_all` a silent no-op, otherwise). Backend type/lint: none configured yet. Frontend: `npx tsc -b` (type-check) and `npm run build` (full build) in `app/frontend`.

The `uv`-managed `pyproject.toml` pins `tool.uv.index` to plain PyPI — this environment's default index (a Databricks proxy) is unreachable from here, so don't remove that override.

## Stack

- **Backend** (`app/backend`): FastAPI + SQLAlchemy 2.0 + PostgreSQL, managed with `uv`. `app/models.py` has the ORM models, `app/schemas.py` the Pydantic I/O types, `app/services/` the business-rule and document-generation logic (see below), `app/routers/` the REST endpoints, `app/seed.py` the demo data. The old `construction_app/` repo's plain dataclasses (now only in git history, see `git show HEAD:construction_app/models/project.py` etc.) informed field naming but weren't reused directly — this is a richer schema with real relationships.
- **Frontend** (`app/frontend`): Vite + React + TypeScript + React Router + TanStack Query, built against `app/frontend/src/styles/tokens.css` (a verbatim copy of `design/styles.css` — don't fork it; if the design system changes, recopy). `src/nav.ts` defines the 7 numbered workflow steps + 5 Company items (Analytics, Operational Reconciliation, **Import from Drive**, **Settings**, Business Expenses) shared by the desktop sidebar and mobile tab bar/menu. `src/context/ProjectContext.tsx` tracks the "currently selected project" (persisted to localStorage) that steps 3–7 operate on.
- **The app UI is bilingual (English/Spanish) — generated documents are not.** `src/i18n/` (`index.ts`, `en.json`, `es.json`) wraps the app in `react-i18next`; every page/component calls `useTranslation()` and renders labels/buttons/headings via `t("namespace.key")`, one namespace per page (`nav.ts`'s own labels are translation keys too, resolved at render time in `Sidebar.tsx`/`MobileShell.tsx`, not literal strings — the nav relabels itself immediately on a language change). The language choice lives in `localStorage` (`cabrera-language`) via `setAppLanguage()` and is set from **Settings** (`SettingsPage.tsx`, `/settings` — also where Team & Users management lives now, folded in rather than kept as its own nav item). **What's translated vs. not** is a deliberate line, not an oversight: UI chrome (labels, buttons, headings, empty states, confirmation dialogs) is translated; actual contract/business data a user types or that gets extracted — milestone titles, payment/warranty terms text, scope text, project type, the generated Contract Package/Change Order PDFs themselves — stays exactly as entered/extracted, always in English, since CLAUDE.md's "reuse the Drive template text verbatim" rule and Cabrera's actual CSLB-compliant contract template are English-only. `StateViews.tsx`'s `StatusTag` translates backend status enum values (`status.*` keys, with the raw value as fallback via i18next's `defaultValue` so an unmapped status still shows something rather than nothing) — a real backend status is data, but showing it as a readable word is chrome.
- **Projects page supports delete and manual contract-amount correction** — `ProjectsPage.tsx`'s Selected Project panel has a Delete button (`DELETE /projects/{id}`, with a confirm dialog) and an inline-editable Contract Value (pencil icon → `PATCH /projects/{id}/estimate`, sets `Estimate.total_override`). Deleting a project cascades its estimate/scope-schedule/milestones/invoices/contract-package/change-orders; receipts and bank transactions are unlinked back to "unassigned" rather than deleted, since they represent real money that moved.
- **QuickBooks is real, not mocked** — `app/backend/app/services/quickbooks_oauth.py` (OAuth2: connect/callback/refresh/disconnect, tokens in the single-row `quickbooks_connection` table) and `quickbooks_service.py` (estimate + customer lookup only — no invoice/payment writes, deliberately, since this is wired to the real production company). `routers/projects.py`'s `fetch_estimate` uses the real service once connected, falling back to `mock_integrations.py`'s fixtures (`1042`, `2091`) otherwise so the screen still works pre-connection.
- **Google Drive/Sheets is real, not mocked** — see "Integrations" below. `mock_integrations.py`'s fake folder/Sheet IDs are only the fallback when Google Workspace isn't connected. A project's `drive_folder_id` can also be set/corrected by hand — `ProjectsPage.tsx` shows a pencil-edit field for it once a project's contract is `signed`, for a folder the automatic Drive › Projects scan didn't find (see `GET /projects/drive-importable`'s "manual folder entry" below) or a project created before Google was ever connected; `PATCH /projects/{id}/drive-folder` accepts either a pasted Drive URL (any common shape) or a bare folder ID. **Adobe Sign is still mocked, and the UI says so honestly** — `mark-signed` just flips the Contract Package's status to `signed`, no real agreement is ever created or sent. The "approved" and "out_for_signature" steps on `ContractPackagePage.tsx` are deliberately framed as a manual workflow now (not "Send for Signature via Adobe Acrobat Sign", which implied automation that was never real): download the generated PDF, send it for signature yourself via Adobe Acrobat Sign (or wherever), then come back and click through the app's own status buttons ("Mark as Sent for Signature" / "Mark as Fully Signed") purely to track where it is — the status machine itself (draft → approved → out_for_signature → signed) stays real and useful even though nothing automated happens at those transitions.
- **Contract/change-order PDFs are real**, not mocked: `templates/Cabrera_Construction_Home_Improvement_Contract.pdf` has genuine AcroForm fields (confirmed via `pypdf`), filled in `app/backend/app/services/documents.py`. The combined Contract Package PDF merges, in order: the filled contract template, a generated Scope & Payment Schedule page (`reportlab` platypus — real tables, not hand-positioned text lines; white background, no fills, deliberately), then the Estimate attachment — either the REAL uploaded estimate PDF when one exists (`Estimate.source_file_id`, see "Estimate document" below), or a minimal `generate_estimate_summary_page` (just the estimate number and total) when it doesn't, rather than a reconstructed line-item recreation. Page 1's `doc4`/`doc5` text fields (blank in the raw template) are filled with "Project Scope and Payment Schedule" / "Estimate" to match this merge order. The approximate completion date field is computed fresh from the LAST milestone's own `due_date` at fill time, not trusted from `project.end_date` (which can go stale). The subcontractors question (`sub_yes`/`sub_no`) is hardcoded to "No" for now — both are independent checkbox widgets, not one radio group, and the template ships with `sub_yes` pre-checked by default, so clearing it explicitly (not just checking `sub_no`) is required or both end up checked.
  - **Estimate document** — `Estimate.source_file_id` means "a real, user-uploaded PDF of the actual estimate," not a generated recreation (a prior version auto-generated+uploaded a `reportlab` recreation at project creation and set this field from THAT, which meant the Contract Package's last page always showed a synthetic recreation — garbled for anything without a real QuickBooks DocNumber, e.g. "QuickBooks Estimate DOC-Pasted notes" for a pasted-text estimate). Project creation no longer touches this field at all now; it's set only via `POST /projects/{id}/estimate/upload-pdf` (a plain "attach this exact file," no extraction), which the Scope & Payment Schedule screen exposes as an "Upload PDF" control next to an editable Estimate Number field (`PATCH /projects/{id}/estimate`, which now updates `total_override` and/or `estimate_number` independently — each only touched when actually present in the request body, checked via Pydantic's `model_fields_set`, since `total_override`'s own `None` means "clear it" and would otherwise wipe an existing override on a request that only meant to update the number). The Estimate Upload screen shows a hint pointing at this after a QuickBooks fetch, since a QB-sourced estimate has no file behind it at all until the user exports and uploads one.

## Production deployment (app.cabrera.construction on Google Cloud Run)

`cabrera.construction` (root domain) is hosted on **Squarespace**, which cannot run a custom backend or proxy a subpath to one — there is no `/app` path under the Squarespace site. The app instead gets its own **subdomain**, `app.cabrera.construction`, pointed at a separate host: **Google Cloud Run** (the user already has a GCP project for the Drive/Sheets integration). This is a plain root-domain deployment on that subdomain, not a subpath one — don't reintroduce `/app`-prefix handling (a Vite `base`, a router `basename`, a separate `VITE_API_BASE`) if asked to revisit this; it was tried and deliberately reverted once the Squarespace constraint came up.

- **One Cloud Run service serves both the API and the frontend**, same-origin — no reverse proxy needed. `Dockerfile` lives at the repo root (`cabrera_construction_app/Dockerfile`, **not** `app/Dockerfile`) — its build context has to be `cabrera_construction_app/`, because it needs to see both `app/` and `templates/`, which are siblings, not parent/child (`gcloud builds submit --tag <image> .` run from `cabrera_construction_app/`, not from `app/`). It builds the frontend in a Node stage, then copies `frontend/dist` into the Python runtime image alongside `templates/`. `.gcloudignore` (same directory) keeps the upload small by excluding `design/`, `node_modules/`, etc. `app/backend/app/main.py` mounts the built frontend: `/assets/*` as static files, and a catch-all route serves `index.html` for anything else not under `/api/*` (so a hard refresh on e.g. `/projects` still works — SPA fallback). This mount is gated on the `FRONTEND_DIST_DIR` env var, so it's a no-op in local dev (where the Vite dev server serves the frontend instead).
- **Database**: Cloud Run is stateless — Postgres needs to be **Cloud SQL**, connected via the Cloud SQL Auth Proxy socket Cloud Run provides automatically when you pass `--add-cloudsql-instances`. `DATABASE_URL` becomes `postgresql+psycopg2://USER:PASSWORD@/DBNAME?host=/cloudsql/PROJECT:REGION:INSTANCE` (note: no host/port before `?host=` — it's a Unix socket).
- **Env vars for the Cloud Run service** (set via `--set-env-vars` or `--update-secrets` for the sensitive ones): `DATABASE_URL`, `FRONTEND_BASE_URL=https://app.cabrera.construction`, `FRONTEND_DIST_DIR=/app/frontend_dist` (matches the Dockerfile), `QUICKBOOKS_REDIRECT_URI=https://app.cabrera.construction/api/integrations/quickbooks/callback`, `QUICKBOOKS_CLIENT_ID`, `QUICKBOOKS_CLIENT_SECRET`, `QUICKBOOKS_ENVIRONMENT=production`, `CORS_ORIGINS=["https://app.cabrera.construction"]`.
- **QuickBooks app URLs** (developer.intuit.com → Keys & OAuth / App URLs): Host Domain `app.cabrera.construction`; Launch URL `https://app.cabrera.construction`; Connect/Reconnect URL `https://app.cabrera.construction/api/integrations/quickbooks/connect`; Disconnect URL `https://app.cabrera.construction/api/integrations/quickbooks/disconnect-callback` (handled by `routers/quickbooks.py`'s `disconnect_callback` — Intuit redirects here when a user disconnects from inside QuickBooks itself, as opposed to this app's own Disconnect button). Register the production redirect URI *alongside* the `localhost` one in Keys & OAuth, not instead of it.
- **DNS**: once `gcloud run domain-mappings create` gives back its target records, add them wherever `cabrera.construction`'s DNS is actually managed (confirm this — Squarespace may have taken over DNS when the site was set up there, even if the domain was originally registered through Google Domains) as a record for the `app` subdomain specifically. The root domain and Squarespace's own records are untouched.

## Domain model (build against this, not intuition)

The app runs a residential remodel from QuickBooks estimate to close-out, for Cabrera Construction (Lic. #1135927). Core flow, in order: **Estimate → Project → Scope & Payment Schedule → Contract Package → (Change Orders / Invoices / Receipts during construction) → Reconciliation & Close**. Company-wide views sit on top: Analytics, Operational Reconciliation (bank matching), Business Expenses, Team & Users.

Key entities, per Design Document §05 (extend the old repo's dataclasses where noted; everything else is new):
- `Project` (extends `models/project.py`): name, project_type, customer name/phone/email + property address (from estimate), start/end date, status (`active`|`completed`|`on_hold`), `drive_folder_id`, `sheet_id`, `imported_at` (set only when the project came from `/projects/drive-import/{id}/confirm` — null for a project created from a fresh estimate; distinguishes the two in the UI).
- `Estimate` (extends `models/estimate.py`): estimate_number, date_issued, `EstimateLineItem[]` (section, qty, unit, unit_price), tax_rate, permit_fees, discount, `source_file_id` (the generated Estimate PDF — real, uploaded to the project's Drive folder at project-creation time when Google is connected, not deferred until Contract Package approval), `total_override` (manual correction when extraction got the total wrong; takes precedence over the computed total when set, via `PATCH /projects/{id}/estimate`). `total` is computed (subtotal + tax + permits − discount) unless overridden.
- `Milestone` (extends `PaymentScheduleItem`): number (0 = initial deposit), title (`Text`, not a capped varchar — see "Known gotchas"), deliverable, scope_verification, due_date, amount, status (`scheduled`|`invoiced`|`partial`|`paid`).
- `ScopeSchedule` (new): project_id, contract_date, contract_type, payment_terms (`Text`), `Milestone[]` (must sum to contract total), `MaterialItem[]` (category, qty, supplied_by, installed_by, notes), warranty_terms, `drive_file_id`.
- `ContractPackage` (new): project_id, description (auto-summarized, user-editable), disclosures, ordered `attachments` list, status (`draft`|`approved`|`out_for_signature`|`signed`), approved_by/approved_at, `drive_file_id`, `adobe_agreement_id`.
- `ChangeOrder` (new): contract_id, number (`CO-##`), `owner_signed_at`/`contractor_signed_at` (both required to take effect), `parts_changed` (scope|price|payments|completion|materials|subcontractors), scope, amount_added/amount_subtracted, `milestone_changes: [{milestone_id, delta}]`, new_completion_date, uses_subcontractors, status (`draft`|`out_for_signature`|`signed`).
- `Invoice` (extends `models/invoice.py`): invoice_number, amount, date_issued/due_date, status (`draft`|`open`|`paid`|`void`), milestone_id; **replace the repo's `stripe_invoice_id` with `qb_invoice_id`**.
- `Receipt` (new): date, description, amount, type (`payment`|`expense`), `project_id` nullable (null = business expense), `needs_project` bool, milestone_id (payments only), source (`quickbooks`|`drive_folder`|`manual`|`bank`), `drive_file_id`.
- `BankTransaction` (new): import_id, account (BofA last 4), posted_date, description, amount (± = deposit/debit), vendor (normalized), receipt_id (nullable match), match_status (`matched`|`possible`|`rejected`|`unmatched`), fingerprint (date+amount+description, for re-import dedupe).

Relationships: `Project` 1—1 `Estimate`; `Project` 1—1 `ScopeSchedule` 1—n `Milestone`; `Project` 1—1 `ContractPackage` 1—n `ChangeOrder`; `Milestone` 1—1 `Invoice`; `Project` 1—n `Receipt`. Reconciliation and Analytics are derived views, not stored tables.

Roles: **Owner/Admin** (full access, signs as Contractor, closes projects, manages users), **Project Manager** (can approve contract packages without Owner sign-off; cannot manage users or close projects), **Customer** (no login — signs via Adobe Acrobat Sign, pays via QuickBooks).

### Business rules that must be enforced server-side (README has the full list)
- Milestone schedule must sum to 100% of contract total before saving; deposit (milestone 0) ≤ min($1,000, 10% of contract).
- Revised contract total = estimate total + Σ(signed change-order deltas). A change order only affects totals/milestones/dates once **both** Owner and Contractor have signed.
- Invoice amount = milestone amount + signed CO deltas for that milestone; due date = issued + 15 days.
- Balance = revised contract − Σ payment receipts (expenses never reduce balance); "Close Project" only allowed at exactly $0.00.
- Bank matching (Operational Reconciliation): exact-match rule is amount equal to the cent AND normalized vendor match AND date within 3 days; a looser rule produces a "possible match" needing user confirmation. Vendor normalization and matching-window details are in the README "Business rules" section — implement exactly as specified, since analytics and closing depend on it.
- Generated contracts/change orders must reuse the Drive template text **verbatim**, filling only blanks — the one sanctioned addition is the "Previously Signed Contract Price" line on change orders.

## Integrations (setup steps are in README "Integrations: setup guide")

1. **QuickBooks Online (Intuit)** — OAuth2, scope `com.intuit.quickbooks.accounting`. Estimates are looked up by `DocNumber` (the number a user types), not internal `Id`, via the query endpoint. PDF/DOCX/XLSX upload (via Gemini, see below) is the fallback path when there's no estimate number. Invoices are created per milestone; payments arrive via webhook and must be idempotent by QB entity ID.
2. **Document/estimate extraction — multi-provider (Gemini, then Claude, then GPT)** — `app/backend/app/services/gemini_service.py` orchestrates across up to three AI providers rather than depending on one. For a given document/paste, it tries Gemini first (if `GEMINI_API_KEY` is set), then Claude via `anthropic_service.py` (if `ANTHROPIC_API_KEY` is set), then GPT via `openai_service.py` (if `OPENAI_API_KEY` is set) — skipping any that aren't configured, and moving to the next one if a provider's model runs but doesn't find usable information (`found: false`, or no line items/milestones) in that particular document. The first provider to return something usable wins; if every configured provider comes up empty, the error lists what each one said, not just the last one tried. This exists because a single model occasionally can't find an estimate in a document that clearly has one (seen in production with informal pasted notes) — a second or third model is a real fallback, not just redundancy. `gemini_service.py` keeps its name and its public functions (`extract_estimate_from_document(s)`, `extract_estimate_from_text`, `extract_historical_project`, `GeminiExtractionError`) for backward compatibility with its router callers, even though it's no longer Gemini-only internally. `any_provider_configured()` is what routers check before falling back to `mock_integrations`' demo data (replacing a plain `settings.gemini_api_key` check). Only Gemini is used for `summarize_scope()` (cleaning up a QuickBooks estimate's memo text) — that one stays single-provider since it already degrades gracefully to the raw, unsummarized text rather than needing a fallback chain.
   - **Shared input handling** (`document_text.py`, used by all three providers): Accepts PDF (sent to each provider natively — Gemini `inline_data`, Claude a base64 `document` content block, GPT a base64 `input_file` via the Responses API — all three have real document/table understanding for PDF), `.docx` (flattened to plain text via python-docx — none of the three have native .docx understanding), `.xlsx` (flattened to plain text via openpyxl, same reason), and a native Google Sheet living in a Drive folder (no file extension, mimeType `application/vnd.google-apps.spreadsheet` — has no raw bytes of its own, so `google_service.py` renders it to PDF via Drive's `/export` endpoint first, then it goes through the normal PDF path). A real "Project Scope and Payment Schedule" document is commonly one of these spreadsheet forms, not a PDF or Word doc — one sheet, one header row, one row per payment phase. An unreadable `.docx`/`.xlsx` (an old `.doc` renamed, a quirky export from another app) is validated **once**, up front, before any provider is tried — the file itself being unreadable isn't a reason to burn three paid API calls finding that out three times, and `document_text.DocumentReadError`'s message points the user at `POST /estimates/paste` (`extract_estimate_from_text`, "Or paste the text directly" on the Estimate Upload screen) as the fallback.
   - **Shared prompt/schema** (`ai_schema.py`): the extraction instructions and response shape are defined once and used by all three providers, so prompt engineering isn't maintained three times and results stay comparable across providers. Gemini keeps its own literal schema copy in its own dialect (uppercase type names) since that path predates the multi-provider refactor and is already proven; `ai_schema.py`'s versions are plain JSON Schema with every field nullable-but-required (`"type": ["string", "null"]`, always listed in `required`) — the shape OpenAI's Structured Outputs **strict mode** requires, which Claude's tool-use schema tolerates fine too. The extraction prompt explicitly separates two concepts that are easy to conflate: **line_items** (the cost breakdown — materials/labor/demo) and **milestones** (the payment schedule — deposit + numbered payments). A document can have either, both, or neither; a payment-schedule-only document (common for informal job notes) is handled, not rejected. Milestone titles are cleaned up from garbled OCR/typos into short standard construction terms ("FRAIMING RAUGE" → "Rough Framing"); `payment_terms`/`warranty_terms` are copied close to verbatim instead, since those are contract language, not prose. When milestones are extracted, `POST /projects` pre-fills the new project's Scope & Payment Schedule with them instead of leaving that screen's generic two-milestone default. A `total_mismatch` warning is surfaced (not silently resolved) whenever the document's own stated total disagrees with the sum of its extracted line items/milestones by more than $1 or 1%.
   - **Untested against real Claude/GPT accounts** — Anthropic's and OpenAI's exact current API shapes (Claude's `/v1/messages` tool-use, OpenAI's `/v1/responses` with `input_file`/Structured Outputs) were implemented to documented conventions and verified with mocked HTTP calls (dry-run tests), not a real account — neither existed for this project when this was built. If one of them starts failing after working before, check that provider's current API reference first; a failure there doesn't affect the other configured providers, since each is tried independently and a failure just moves to the next one in the chain.
3. **Google Workspace (Drive + Sheets) — real, not mocked** — `app/backend/app/services/google_service.py` (OAuth in `google_oauth.py`, mirroring `quickbooks_oauth.py`). Drive folder layout is `Projects/{Customer} – {Street}/{Project Type}/` — one project gets its own subfolder (found-or-created) under a shared customer+address folder, so a second project at the same address (e.g. a kitchen remodel, later a bathroom job) doesn't collide with or duplicate the first. A `Templates` folder and per-project/company Sheets for reconciliation and analytics sit alongside. Exact structure (Change Orders/Invoices/Receipts subfolders) is in the README. The project's Drive folder has nothing in it but the Reconciliation Sheet until the user uploads a real estimate PDF (see "Estimate document" above) or approves the Contract Package (which files the full combined PDF) — project creation itself no longer auto-generates and uploads a placeholder Estimate PDF there.
   - **Importing a pre-existing project is a separate pipeline from creating a new one**, not a variant of the new-estimate wizard, with its own nav tab — **Import from Drive** (`DriveImportPage.tsx`, `/import-from-drive`), not part of Estimate Upload. `GET /projects/drive-importable` lists un-imported folders (recognizing both the new `{Customer}/{Project Type}` shape and old flat `{Customer} – {Street}` folders from before this app existed, which have no project-type subfolder); `POST /projects/drive-import/{folder_id}` previews one (Gemini reads whatever's in there — contract, estimate, payment schedule — into `schemas.DriveImportPreview`); `POST /projects/drive-import/{folder_id}/confirm` creates the full project — Estimate, Scope & Payment Schedule with those milestones, and a Contract Package already `status="signed"` (skipping draft/approve/send-for-signature, since it was signed before this app existed) — reusing the existing Drive folder rather than creating a new one. Confirming shows an explicit success panel (customer name + "View in Reconciliation" link) rather than silently redirecting — a record was genuinely created, and that should be visible, not inferred. `GET /projects/drive-imports` is the import history (`DriveImportHistoryItem[]`): every imported project with its `imported_at` date and what was actually extracted (read back from the created records, not a separate extraction log), shown expandable on the Import from Drive page. `GET /projects/drive-importable`'s scan only looks directly under Drive › Projects — a real project folder anywhere else in the connected account (nested deeper, under a Shared Drive, organized differently) never shows up there even though the app can read it fine once it has the folder ID. The Import from Drive page's "manual folder entry" field is the fallback for exactly that: paste the folder's Drive link (any common shape) or its bare ID and it runs the same preview straight away, bypassing the scan entirely — the same `extractDriveFolderId`-style URL parsing is duplicated once more server-side for `PATCH /projects/{id}/drive-folder` (see above).
4. **Adobe Acrobat Sign** — REST v6: upload transient document → create agreement with Owner + Contractor as signers → webhook on completion → replace the draft PDF in Drive. Viewing uses Adobe's PDF Embed API, proxied through the backend (Drive file stays private).
5. **Bank of America** — no API in v1; user-uploaded CSV/QFX file, parsed and vendor-normalized per the README's rules, matched against receipts.

All OAuth secrets and refresh tokens must stay server-side/encrypted; verify webhook signatures (Intuit `intuit-signature`, Acrobat Sign client ID header).

### Failure handling (Design Document §06)
- A disconnected service turns its header connection tag into a warning with "Reconnect"; actions that depend on it are disabled with an explanation, rather than allowed to fail silently.
- If the estimate PDF can't be parsed, the upload screen shows which fields are missing and **creates nothing**.
- Webhook and Drive folder-scan events must be idempotent by external/file ID so a receipt is never double-counted.
- If a Drive/Sheets write fails, keep the local record and retry — surface "last synced" in the UI rather than blocking.

## Implementation order (Design Document §09, decided Sep 28, 2026)

## Known gotchas (learned the hard way, in production)

- **No Alembic** — `app/backend/app/main.py`'s `_run_light_migrations()` runs a handful of idempotent raw-SQL statements (`ADD COLUMN IF NOT EXISTS`, `ALTER COLUMN ... TYPE ...`) on every startup, since `Base.metadata.create_all()` only creates missing *tables*, never alters an existing one's columns. Add new statements here (never destructive — `IF NOT EXISTS`/widening-only) when a model change needs to reach a table that's already live in production.
- **Route registration order matters for literal-vs-parameterized paths** — FastAPI/Starlette matches routes in registration order within a router. `GET /projects/drive-importable` must be registered *before* `GET /projects/{project_id}`, or `"drive-importable"` gets swallowed by `{project_id}`'s `int` parsing and 422s before ever reaching the real handler. Any new literal-path route under `/projects/...` needs to go above the `{project_id}` catch-all, not below it.
- **Free-form extracted text needs `Text` columns, not capped `varchar(n)`** — a real signed contract's payment-terms clause, a milestone title, or a line-item description can run far longer than demo/seed data ever would. A `varchar(n)` here raises `psycopg2.errors.StringDataRightTruncation`, which crashes the *whole* request with an uncaught 500 — and since this fires mid-transaction, it can happen *after* other steps in the same request already succeeded, silently losing nothing but also confirming nothing. `ScopeSchedule.payment_terms`, `Milestone.title`, and `EstimateLineItem.description` are `Text` for exactly this reason (this took several rounds of production tracebacks to actually pin down) — be wary of adding a new `String(n)` column for anything Gemini extracts from an arbitrary uploaded document.
- **Best-effort post-commit Drive/Sheets writes must catch `httpx.HTTPError`, not just this app's own exception types** — a token-refresh hiccup or network blip raises a raw `httpx.HTTPStatusError`/`TransportError`, not `GoogleNotConnected`/`GoogleApiError`. An except clause that only catches the latter two lets the former crash the whole request *after* the real DB commit already succeeded — the record exists, but the response never confirms it and the frontend has no way to know. (`routers/projects.py`'s best-effort Drive blocks catch `(GoogleNotConnected, GoogleApiError, httpx.HTTPError)` together for this reason.)
- **Never pass a non-string straight into `new Error(...)`** — `app/frontend/src/api/client.ts`'s `request()` coerces `body.detail` defensively (a plain string, a FastAPI 422 validation-error array, or an unexpected object) before constructing an `ApiError`. Skipping this silently stringifies any object/array to the literal text `"[object Object]"` instead of throwing something readable — a genuinely confusing bug to chase blind.
- **Cloud Run behind a Serverless NEG load balancer has no separate backend-service timeout** — `gcloud compute backend-services update --timeout` errors on a Serverless NEG backend ("not supported"). The real governing timeout for the whole request path is Cloud Run's own `--timeout` (default 300s, settable via `gcloud run services update --timeout`). Any synchronous request (a Gemini extraction, say) needs its worst-case retry budget to stay comfortably under that.
- **Gemini retries are deliberately bounded, not maximized** — `gemini_service._post_with_retry`'s retry count and per-call timeout are tuned so a request fails clearly in under ~2.5 minutes rather than potentially hanging for 6+. These calls run synchronously inside a request a person is actively waiting on; a real Gemini capacity outage can outlast any retry budget that's still reasonable for an interactive screen, so failing fast with a clear error beats a long silent hang.
